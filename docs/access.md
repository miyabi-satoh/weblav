# 公開範囲と権限

## 公開範囲と匿名閲覧

### 公開範囲

`contents.visibility` は `public` / `authenticated` / `private` / `hidden` の4値。
`private` と `hidden` の設計は、本節から 7. までに書く。

| 値 | 画面の表記 | 閲覧の場で見える人 | 管理画面の一覧に出る相手 |
|---|---|---|---|
| `public` | 誰でも | 匿名を含む全員 | ログイン済みの全員 |
| `authenticated` | ログインした人 | ログイン済みの人 | ログイン済みの全員 |
| `private` | 作成者のみ | 作成者 (`contents.created_by`) だけ | 作成者と `admin` |
| `hidden` | 非表示 | 誰にも出ない | ログイン済みの全員 |

- 作成時に、セッションのユーザーを `created_by` に入れる。以後、管理者の付け替え (→ 「ロールと操作」) とユーザーの削除 (→ 「ユーザーの削除と作成者」) 以外では書き換えない。
- `created_by` が NULL の行は作成者なし。作成者のユーザーが削除された行がこれにあたる。
- `private` にできるのは、作成者と `admin`。`created_by` が NULL の行は誰も `private` にできず、`private` で `created_by` が NULL の行は生まれない。
- `group` も `private` にできる。中に置けるものは「作成者のみのグループ」で縛る。

`admin` 限定の公開範囲は設けない。準備中のものは `hidden` と、フォルダーの除外のパターンで隠せるため。

### 作成者のみのグループ

`private` のグループには、そのグループの作成者の `private` だけを置ける。管理者でも例外にしない。自分だけのために使う括りを、ほかの人に見えない形で作れるようにするため。

- 作成・親の付け替え・公開範囲の変更で、親が `private` のグループなら、置くものが `private` で、作成者が親と同じでなければ 422 (`privateGroupNeedsOwnPrivate`)。
- グループを `private` にするのは、直下の子がどれもグループの作成者の `private` のときだけ。そうでなければ 422 (`groupChildrenNotOwnPrivate`)。孫より下は、子が `private` なら同じ決まりで揃っている。
- 作成で公開範囲の指定が無く、親が `private` のグループなら `private` にする。中にはそれしか置けないので、指定の無い作成を 422 にしないため。
- 子の公開範囲まで `private` に揃えるのは、中身の行を1行ずつの判定に乗せるため。管理画面の一覧・`{id}` を取るエンドポイントの 404・ユーザーの削除は、どれも行の公開範囲と作成者だけを見ている (→ 「管理用の一覧が `user` に見えること」・「ロールと操作」・「ユーザーの削除と作成者」)。子が `public` のまま中に入れられると、これらすべてに祖先を辿る判定を足すことになる。

### 匿名閲覧の受け口

- `AuthUser` (未ログインなら401) に加えて、**未ログインでもエラーにしない
  extractor `Viewer`** を `src/auth.rs` に追加する。セッションを読み、
  ログイン済みならユーザーを、未ログインなら「匿名」を表す値を返す。
- 閲覧系のハンドラ (`list_contents` / `browse_group` / `browse_folder` /
  `download_content` / アーカイブ一覧・アイテム配信) の引数を
  `AuthUser` から `Viewer` に差し替える。
- 判定はヘルパーに集約し、閲覧の場の一覧に出すかと、単体で開けるかを分ける。
  - `can_list(viewer, content)`: 一覧に出すか。`public` は常に真、`authenticated` は `viewer` がログイン済みなら真、`private` は `viewer` が作成者のときだけ真、`hidden` は常に偽。`admin` でも他人の `private` は偽。
  - `can_open(viewer, content)`: 単体の取得・配信を許すか。`can_list` が真のものに加えて、`hidden` は `viewer` がログイン済みなら真、他人の `private` は `viewer` が `admin` なら真。どちらも、管理用の一覧 (→ 「管理用の一覧が `user` に見えること」) に出るものを、管理画面や編集ページから開けるようにするため。そこから開くときも閲覧用の画面と API を使うので、URL を直接開いた場合も同じ判定になる。
  - フォルダーの中のファイル・サブフォルダーと一覧の表示のアイテムは、どちらもこれに加えて絞り込みに当たることを要求する (→ folders.md「見せるものの絞り込み」)。書き換えられる人も同じ。
  - 単体で開く判定は、対象ノードに加えて祖先のグループすべてにも通す (→ 「祖先のグループを辿る」)。
- 一覧は取得した後に `can_list` で絞る。判定を1箇所に保つため。単体取得・ダウンロードは取得後に `can_open` を通す。
- グループ閲覧 (`browse_group`) で、対象グループか祖先のグループが閲覧者の閲覧の場の一覧に出ないもの (`hidden` か、`admin` が開いた他人の `private`) のときは、直下の子を `can_list` ではなく `can_open` で絞る。管理画面から中身を確かめに開いたものなので。`can_open` で絞るので、他人の `private` は `admin` にしか並ばない。
  このグループは閲覧の場のどこにも並ばないので、閲覧の場の一覧に `hidden` が混ざることにはならない。

ステータスコードの使い分け。

| 状況 | コード | 理由 |
|---|---|---|
| 匿名が `authenticated` / `private` / `hidden` のコンテンツを要求 | 401 | ログインすれば開ける可能性があるため。`private` の作成者が、ログインしていない端末で自分用のリンクを開いたときにも迷わない。フロントは戻り先 URL 付きで `/login` へ誘導する |
| ログイン済みで、作成者でも `admin` でもない人が `private` のコンテンツを要求 | 404 | 存在ごと隠す |
| 存在しない id | 404 | |
| フォルダーの絞り込みで外れたもの | 404 | ログイン済みの閲覧者に対しても隠す。編集できる人にも同じものだけを見せるため |

ログイン済みの人に対して存在を隠すのは、絞り込みで外れたものと他人の `private` だけ。
匿名に対しては、公開範囲の不足を 401 (ログインを求める) で統一する。
id は連番なので、匿名に何かがあると分かること自体の害は小さい。

### 祖先のグループを辿る

公開範囲は親グループから継承する。グループの中のコンテンツは、自分の公開範囲と、祖先のグループすべての公開範囲をどれも満たす相手にだけ見える。
閲覧時は、対象ノード自身に加えて、祖先のグループすべてを判定に通す。

- 単体で開くときは、祖先のグループそれぞれにも `can_open` を通す。1つでも通らなければ、対象ノード自身が通らなかったときと同じコード (匿名は401、ログイン済みは404) を返す。
- 一覧は、親を開けることを確かめてから子を並べるので、並べる子ごとに祖先を辿り直す必要は無い。トップはルート直下だけを並べる。
- 祖先はグループだけ。祖先で弾かれるのは、匿名と、他人の `private` のグループの中を開こうとした `user` (404)。後者の中身は、どれもそのグループの作成者の `private` なので (→ 「作成者のみのグループ」)、行そのものの判定でも弾かれる。
- **閲覧の経路を1つも取りこぼさないこと**。祖先を辿り忘れた経路があると、隠したつもりのグループの中身が匿名に見える。辿る処理は1つのヘルパーに集約し、単体で開く全経路 (グループ・フォルダー・ファイル配信・アーカイブ) がこれを呼ぶ。
- 祖先は再帰 CTE の1回のクエリで取り、パンくずにも同じ結果を使う (`ensure_viewable`)。

### フロントエンドのガード反転

- 未ログインを一律 `/login` へリダイレクトしない。
- ログインを要求するのは `/admin/**` と、コンテンツの編集ページ (`/contents/[id]/**`)、自分のアカウント (`/account`) のみ
  (`frontend/src/lib/auth.ts` の `isProtectedRoute` が判定する)。
- 閲覧系 API が 401 を返したときのみ、戻り先 URL を付けて `/login` へ誘導する。
  404 は「存在しない」として素直に表示する (→ 「匿名閲覧の受け口」の表)。
- ヘッダーには未ログイン時「ログイン」、ログイン時はユーザーメニューを出す。
  - 管理画面への入口とログアウトはメニューの中に置く。スマートフォン幅でヘッダーに収めるため。
  - メニューのボタンにはユーザー名を出す。共有端末で、誰がログインしたままかを開かずに分かるようにするため。
- 閲覧の一覧で、`private` の行 (作成者にだけ届く) には「作成者のみ」の印を出す (→ ui.md「UI 全般」)。閲覧用のレスポンス (`ContentResponse`) に、`private` かどうかを含める。

### 書き換えられる行

閲覧用のレスポンス (`ContentResponse`) に、閲覧者がそのコンテンツを書き換えられるか (`canEdit`) を含める。判定は `ensure_editable` と同じ (`admin` か作成者) で、匿名には常に偽。ホーム・グループの一覧の行に、編集の鉛筆を出すかを画面が決めるのに使う (→ ui.md)。


### 非表示のコンテンツ

非表示 (`hidden`) のものは閲覧の場のどこにも並ばないので、後から探して開けるよう、別の一覧を持つ。戻すのは、ほかの公開範囲の変更と同じ口で行う。

- `GET /contents/hidden` は、`admin` には全部、ほかの人には自分が作成者のものだけを返す。行の形と並び順 (`sort`) は閲覧の一覧 (`GET /contents`) と同じ。`/auth/me` には、その件数 (`hiddenContentCount`) を添える (ユーザーメニューに出す)。
- 非表示にする前の公開範囲を `contents.visibility_before_hidden` に覚える。共有の中から「ホームに載せる」で非表示のものを戻すとき、公開範囲の指定が無ければこれに戻す (覚えていなければ `authenticated`。`public` に戻すと、隠していたものを匿名にまで見せてしまうため)。書くのは DB のトリガーの1箇所 (`hidden` になったときに前の値を書き、`hidden` でなくなったときに消す)。公開範囲を変える箇所ごとに書くと、新しく足した箇所で書き忘れるため。

## 親が外れるときの公開範囲

公開範囲の組み合わせで保存を拒むことはしない。
**親の付け替えやグループの削除で実際の見え方が緩んでも、公開範囲は書き換えない**。保存するのは指定された公開範囲のまま。
操作した人の意図した結果が黙って変わると混乱のもとになるため。
例えば、誤って「ログインした人」のグループに作った「誰でも」のコンテンツを正しいグループへ移したのに、「ログインした人」に変わってしまう。
歯止めは、実際の見え方を操作の前に示すことで設ける。どうするかは操作する人が決める。

実際の見え方は、自分の公開範囲に、祖先のグループの公開範囲のうち最も厳しいものを重ねて決める。

- 厳しさは `public` < `authenticated` < `hidden` の順。
- 自分が `private` なら `private` のまま。`private` の子を見られる作成者はログイン済みで、祖先の `public` / `authenticated` / `hidden` のグループも、自分の `private` のグループも開けるため。祖先に `private` のグループがあれば、自分も `private` に揃っている (→ 「作成者のみのグループ」)。
- 計算はフロントが管理画面の表示のために持つ (→ ui.md「UI 全般」)。サーバーは閲覧のたびに祖先を1つずつ確かめる (→ 「祖先のグループを辿る」)。

| 操作 | 操作の前に示すもの |
|---|---|
| 親の付け替え | 編集ページの公開範囲の欄の下の説明に、新しい親の下での実際の見え方を出す。実際の見え方が緩むときは、種類によらず保存前の確認ダイアログに前と後の見え方を出す |
| グループの削除 (直下の子をルート直下へ昇格) | 削除の確認ダイアログに、昇格で実際の見え方が緩む直下の子を、削除前と後の見え方とともに挙げる。孫以下は親 (昇格した子) が残るので変わらない |

## 権限

### ロールと操作

ロールは `user` (一般ユーザー) と `admin` (管理者) の2段。`user` もコンテンツを作れ、書き換えられるのは自分が作成者のものだけ。`admin` は全部を書き換えられ、ユーザー管理とサーバーの設定も受け持つ。
**`/admin` の下は、画面も API も `admin` 専用にする**。`user` も使うコンテンツの編集ページ (`/contents/[id]`) と、編集ページや追加の窓が呼ぶ API は `/admin` の外に置く。URL を見れば管理者だけのものか分かり、守りを `/admin` の1か所 (画面は `routes/admin/+layout.ts`) で掛けられるため。
`user` は閲覧の画面から作り (「＋ 追加」)、ペンから編集ページを開くので、コンテンツの管理の一覧 (`/admin/contents`) は要らない。

操作ごとに受ける extractor は次のとおり。

| 操作 | extractor |
|---|---|
| 閲覧系すべて | `Viewer` |
| コンテンツの作成 (種別を問わない) | `AuthUser` |
| コンテンツの編集・削除 | `AuthUser` + `ensure_editable` (下記) |
| 非表示のコンテンツの一覧 | `AuthUser` (`admin` には全部、ほかの人には自分が作成者のもの) |
| 再スキャン・見せるものの絞り込みの変更の確認・対象外のタブの一覧 | `AuthUser` + `ensure_editable` |
| 軸 (追加・削除・抽出元・並び順・値の辞書)・表示タイトルのテンプレート (`title_template`) | `AuthUser` + `ensure_editable` |
| コンテンツの `visibility` の変更 | `AuthUser` + ハンドラ内で判定 (下記) |
| 作成者 (`created_by`) の付け替え | `AdminUser` (下記) |
| 管理用のコンテンツの一覧・フォルダーの選択・対象のファイル数 (`/contents/manage`・`/fs/dirs`・`/fs/count`) | `AuthUser` |
| 共有の登録・場所の選び直し | `LocalRequest` + `AdminUser` (→ folders.md「共有」・shares.md「共有の場所の選び直し」) |
| 共有の一覧・名前の変更・削除・権限の設定 | `AdminUser` |
| 共有の中を見る・書き換える | `AuthUser` + 共有ごとのできること (→ shares.md「できること」) |
| 操作の記録 | `AdminUser` (→ operations.md) |
| ユーザー管理 | `AdminUser` |
| サイト設定の取得 | なし (未ログインでも読める。ホームの見出しに使う) |
| サイト設定の変更 | `AdminUser` |
| サーバーの設定 (ポート・アップロードの上限・セッションの有効日数) の取得・変更 | `AdminUser` |
| 詳しいログの切り替え・ログのダウンロード | `AdminUser` |
| バックアップのダウンロード・リストア | `AdminUser` (→ 「バックアップとリストア」) |

表の `AdminUser` のうち、書き換える操作とバックアップの引換券を出す口は `ConfirmedAdmin` で受け、パスワードの確かめ直しも求める。`ensure_editable` を通す書き換えのうち他人のものは `ensure_changeable` で同じく確かめ直す (→ 「操作の前のパスワードの確認」)。

- **エンドポイントは type ごとに分けない**。`create_content` /
  `update_content` / `delete_content` は `AuthUser` で受け、type による権限の差は持たない。
  URL 設計を type で割るとフロント側の分岐が増えるため。
- **書き換える操作は `ensure_editable` を通す**。`user` が書き換えられるのは作成者が自分のものだけで、他人のもの・作成者のいないものは 403。`admin` は全部に許す。
  - 読む操作 (一覧・軸・値の辞書・アイテムの一覧など) は、他人のものでも `user` に許す。見えるものの中身なので、読ませても困らないため。
  - 他人の `private` は、書き換えでも読むのでも 404 (下記)。403 にすると存在が分かるため。
- **`folder` も `user` が作れる**。選べるのは登録された
  「共有」の中だけで、誰が選んでも範囲は同じになるため。
  登録をサーバーの前にいる管理者に限ったこと (→ folders.md「共有」) が、この開放の前提。
  作ったフォルダーの一覧の表示の設定・軸・テンプレートも、作った `user` が設定できる。
- **親の付け替えは、入れる側 (子) の書き換えとして判定する**。自分のコンテンツを他人のグループに入れてよい。グループを削除すると、中の他人のコンテンツもルート直下へ上がる。
- **作成者の付け替えは `admin` だけ** (`PUT /contents/{id}/creator`)。いないユーザーは 422。`private` のグループとその中身は作成者が揃っている必要があるので、揃わなくなる付け替えも 422 (→ 「作成者のみのグループ」)。
- **一覧の表示を使うフォルダーの編集ページは「設定 / 分類 / ファイル」を同列のタブに並べる**。タブごとに URL を分ける (`/contents/[id]`・`/axes`・`/items`)。
  書き換えられない人 (他人のものを開いた `user`) は、編集ページを開くと閲覧画面へ移るので、タブを出し分けない (→ ui.md「UI 全般」)。対象外のタブも含め4つを並べる。
- 作成時の `visibility` はリクエストの値を使う (フロントの既定は `public`)。`user` も選べる。下書きを自分で公開できなければ、下書きとして機能しないため。
- **`admin` の公開範囲の変更に、他人の `private` についての例外を設けない**。ほかの人にできる操作は `admin` にもでき、権限の段を1つの言葉で説明できるようにするため。作成者のいないものを `private` にする更新だけは、見る人がいなくなるので `admin` でも 403。`private` のグループに置けるものの決まりは 422 (→ 「作成者のみのグループ」)。権限の判定 (404・403) の後に確かめる。
- **`{id}` を取る書き込み・管理用のエンドポイントは、`user` から見て他人の `private` なら 404 を返す**。編集・削除・公開範囲の変更に加え、アーカイブの再スキャン・アイテム・軸・値の辞書の各エンドポイントも含む。存在を隠すため (→ 「匿名閲覧の受け口」)。`admin` には通常どおり許す。
- 親の付け替えは、公開範囲の組み合わせでは拒まない。付け替えで実際の見え方が緩んでも、公開範囲は書き換えない (→ 「親が外れるときの公開範囲」)。

- **管理者は、自分自身をユーザー管理から変えられない** (名前・パスワードの再設定・権限・削除。どれも 403)。名前とパスワードは本人と同じくアカウントのページで変え、降格と削除はほかの管理者がする。
  ユーザー管理から自分を変えると、アカウントのページとは別の決まりで同じ値を変える場所が2つになるため (管理者による再設定はリカバリコードも消す)。

### 操作の前のパスワードの確認

ログインしたまま席を離れた画面 (教室の共有の PC など) から、本人を締め出す変更や、ほかの人の持ち物・全体に及ぶ変更をされないよう、次の操作の前にパスワードを確かめ直す。GitHub の sudo mode に倣い、一度確かめたらしばらく聞き直さない。

- **掛ける操作**:
  - 自分のアカウントの操作 (ユーザー名・パスワードの変更・リカバリコードの作成)
  - 管理者だけの操作のうち書き換えるもの全部 (`/admin` の下の書き換えと作成者の付け替え) と、バックアップのダウンロード (全員のパスワードのハッシュが入るため)
  - 他人が作ったコンテンツ (作成者がいないものを含む) の書き換え (編集・削除・公開範囲・軸と表示タイトル)
- **掛けない操作**: 読むだけのもの、自分のコンテンツの書き換え、共有の中の操作、再スキャン。どれも日々の作業で、確かめ直しを挟む手間が大きい。共有の中の操作は管理者がその共有に許した範囲の内、再スキャンはフォルダーを読み直すだけで、持ち主が決めた設定を変えない。
- **仕組み**: セッションに、最後にパスワードを確かめた時刻と、そのときのパスワードの指紋 (ハッシュの SHA-256) を持つ。ログイン (リカバリコードでの戻し・初回セットアップを含む) でも入る。確かめてから `PASSWORD_CONFIRMATION_WINDOW` (`src/auth.rs`) の内で、指紋が今のパスワードと合えば通して時刻を今に延ばし、そうでなければ 403 `password_confirmation_required` を返す。
  指紋を比べるのは、管理者の再設定の後に、古いパスワードで確かめたセッションから、パスワードやリカバリコードを作り直されないため (再設定でコードを消す理由と同じ。→ 「リカバリコード」)。自分でパスワードを変えたセッションは、新しい指紋で確かめた内のままにする。
  401 にしないのは、画面が 401 をログイン切れとしてログインへ送るため。判定の順は、未ログイン (401)・権限 (403 `forbidden`)・確かめ直しの順。
- **確かめ方**: `POST /auth/confirm-password` に今のパスワードを送る。総当たりを防ぐため、ログインと同じレートリミットを掛ける。
  画面は `client` の middleware で 403 `password_confirmation_required` を受けてダイアログを出し、確かめられたら同じ要求を送り直す。操作ごとの画面は確かめ直しを知らずに済む。
  ブラウザーが直接開くダウンロード (バックアップ) は、断られても画面で受けられない。そこで確かめ直しは、画面が送る `POST /admin/backup/ticket` で求め、一度だけ使える引換券を返す。ブラウザーは券を付けて `GET /admin/backup` を開き、サーバーは券がそのセッションで出したもので、出してから `DOWNLOAD_TICKET_TTL` (`src/api/backup/mod.rs`) の内かだけを見る。確かめるのが券を出すときの1回なので、確かめてから取りに行くまでの間に確かめが切れることがない。

### 管理用の一覧が `user` に見えること

`GET /api/v1/contents/manage` は、`path`・公開範囲・作成者を含むコンテンツの一覧で、`AuthUser` で受ける。
コンテンツの管理の一覧 (`admin` 専用) のほか、`user` も使う編集ページ・追加の窓が、親の候補と、親を重ねた見え方の判定に使うため。
`user` にも `path` (サーバー上の絶対パス) が見える。

この一覧は、`private` を除けば `admin` と `user` で同じものを見せる。登録できるのは「共有」の中だけなので (→ folders.md「共有」)、`user` に
見せたくないパスはそもそも登録されない、という運用で成立する。

`ContentResponse` のドキュメントコメントにある「非adminにファイルシステムの
レイアウトを漏らさないため」という記述は、**匿名を含む一般閲覧者向けの
`ContentResponse` にのみ当てはまる**ものとして書き直す
(`AdminContentResponse` 側は `user` にも返す)。実装済み。

`private` は例外で、`user` には自分の `private` だけを返す。
`admin` には全員の `private` を返す。
`hidden` は全員に返す。
一覧の「作成者」に出せるよう、`AdminContentResponse` に作成者のユーザー名を含める (作成者なしなら null)。

### admin の最後の1人

`admin` が0人になる操作 (最後の admin の降格・削除) は拒否する。ユーザー管理 API 側で、更新・削除の直前に
`SELECT COUNT(*) FROM users WHERE role = 'admin'` を同一トランザクション内で
確認する。
`admin` が0人になると、管理画面から戻せなくなるため。
自分自身はユーザー管理から変えられないので (→ 「ロールと操作」)、これに当たるのは2人の管理者が互いを同時に降格・削除するときだけ。

### ユーザーの削除と作成者

ユーザーを削除するとき、そのユーザーが作成者の `private` は `hidden` に変えて残す。消さずに、管理画面でみんなが中身を見て、片付けるか共有するかを決められるようにするため。

- ユーザー削除 API の中で `contents_write_lock` を保持し、1トランザクションで次を行う。
  1. `created_by` がそのユーザーで `visibility = 'private'` の行を `hidden` に更新する。公開範囲の組み合わせの制約は無く (→ 「親が外れるときの公開範囲」)、`private` のグループの中もその人の `private` だけなので (→ 「作成者のみのグループ」)、ほかの人の行の見え方は変わらない。
  2. `created_by` がそのユーザーの行を、すべて NULL にする。
  3. ユーザーを削除する。
- 削除の確認ダイアログに件数を出すため、ユーザー一覧のレスポンスに、そのユーザーが作成者の `private` の件数を含める。
- `created_by` の外部キーには `ON DELETE` を指定しない。上の手順を通らずにユーザーを消そうとすると失敗させ、作成者のいない `private` を作らないため。

### 初回セットアップ

`admin` が1人もいないとき、タスクトレイの「セットアップ」からブラウザーで `/setup` を開き、最初の管理者を作る。サインアップの画面は持たない。
管理者のパスワードを忘れたときの戻り道は、リカバリコード (→ 「リカバリコード」)。
CLI (`weblav-cli --create-user`) は開発・テスト用で、リリース版には入れない (→ distribution.md「コンソールの扱い」)。
入れると、使い方を知っている人なら誰でも、何度でも管理者を足せてしまうため。

- **未セットアップの判定は「`admin` が0人」**。
  「admin の最後の1人」の不変条件 (最後の admin は降格・削除できない) があるので、この状態になるのは最初と、DB を作り直したときだけ。
- **セットアップの口 (`/api/v1/setup/*`) は、接続元と宛先 (`Host`) の両方がループバックの要求だけを通す**。サーバーを動かしている PC の前にいる人だけがセットアップできる。
  接続元だけでは足りない。前段に同じ PC のリバースプロキシを置かれると (→ architecture.md「LAN からの到達性」) LAN からの要求もループバックで届き、名前を 127.0.0.1 に振り直したページ (DNS リバインディング) はブラウザーから見て同一オリジンになってトークンの応答を読めてしまう。
  `Host` が名前のときは `localhost` だけを通す。127.0.0.1 に向いたほかの名前は、リバインディングと区別が付かないため。
  **転送の印 (`Forwarded`・`X-Forwarded-For`・`X-Real-IP`) が付いた要求も通さない**。同じ PC のプロキシ越しに LAN の端末が `Host: localhost` を名乗ると、接続元も `Host` もループバックになり、上の2つでは落とせないため。
  Caddy は既定で `X-Forwarded-For` を付ける。nginx は付けないので、マニュアル (設置する「HTTPS で使う」) で足すよう案内する。
  ヘッダを足さない TCP の転送 (`netsh interface portproxy`・SSH のポート転送など) は見分けられず、防げない。HTTP のリバースプロキシ以外で LAN から届く入口を作らないのは、設置者の責任とする。
  **UAC のような昇格は挟まない**。ループバックの口は昇格と関係なく叩けるので、挟んでも手間が増えるだけで守りにはならない。
- **`bind` にループバックでも `0.0.0.0` でもないアドレスを書くと、この画面は使えない**。その PC 自身からつないでも接続元がそのアドレスになるため。
  セットアップの間だけ `bind` を既定に戻してもらう (マニュアルの「詳しい設定」で案内する)。`bind` を書き換えるのは `config.toml` を触れる人なので、それで足りる。
- **断る理由は区別せず、すべて 404 にする**。
  セットアップ済み・トークンが違う・期限切れ・外からの要求のどれでも同じ応答にして、「この PC にはまだ管理者がいない」ことを LAN に見せない。画面も理由を出し分けず、同じ「使えないリンク」の案内を出す。
  口があること自体は隠さない (隠せない)。`/setup` の画面は配信するフロントエンドに含まれており、メソッド違いには axum が 405 を返す。
- **トークンを要求する**。ループバックに限るだけでは足りない。
  LAN や外部の悪意あるページを踏むと、そのブラウザーから `http://127.0.0.1:<port>/api/v1/setup/admin` へ送らせることができ、送信元はループバックになる。
  推測できないトークン (256bit を16進で渡す) をブラウザー側から添えさせて、これを防ぐ。
- **トークンはプロセスのメモリにだけ置く**。ディスクにも DB にも書かない。
  - 「セットアップ」を押すたびに発行し、その時点で前のものを無効にする。有効期限は10分、管理者を作れた時点で使い切る。
  - トレイは `POST /api/v1/setup/token` で受け取り、`http://localhost:<port>/setup?token=...` を開く。
  - 画面はトークンを URL に持ったままにする。読み込み直しで使えないリンクになるのを避けるため。単発・短命でループバックからしか使えないので、URL に残ることの害は小さい。
  - **発行そのものは誰でも (この PC の中からなら) 要求できる**。そのため、設置中の PC で踏んだ悪意あるページが発行を繰り返し、管理者が開いたタブのトークンを無効にすることはできる。押し直せば済むので、ここは防がない。
- **作れたら、そのままログインさせ、リカバリコード (→ 「リカバリコード」) を見せてから管理画面へ送る**。設置作業がコンテンツの登録へそのまま続く。セッションの張り方はログインと同じ (ID を振り直してから書く)。
- **「admin が0人」の確認から作成までは `users_write_lock` で直列化する** (「admin の最後の1人」と同じ鍵)。確認の後に別の要求が管理者を作ると、この口から2人目を作れてしまう。
- **トレイは3秒ごとに `GET /api/v1/setup/status` を叩き、200 のときだけ「セットアップ」を出す**。
  セットアップが済めば消え、DB を作り直せば出し直す。状態行しか読まないので、トレイに JSON パーサを持たせずに済む。
  本文を読むのは `POST /api/v1/setup/token` の応答だけで、これはトークンだけの `text/plain` にしてある。

### バックアップとリストア

管理画面のサイト設定から、データを1つの zip としてダウンロードし、そこから戻せる。置き場所を知らない管理者でも、入れ直しや PC の引っ越しの前に取っておけるように。
admin が0人のときは、セットアップの画面 (→ 「初回セットアップ」) からも戻せる。

- **zip に入れるのは DB だけ** (`src/api/backup/`)。
  - `manifest.json` (形の版・作った WebLAV の版・日時・DB のマイグレーションの版) と `weblav.db`。
  - 共有の中のファイルと、作り直せるサムネイルは入れない。`config.toml` も入れない (ポートなど、その PC に結びつく値のため)。
- **作るときは、DB を写してから、作りながら送る**。
  - DB は `VACUUM INTO` で作業用ディレクトリへ写す。1つの読み取りの中で写すので、書き込みと並んでも一貫した写しになり、鍵は要らない。
  - 作業用ディレクトリは設定とデータの置き場の中 (`backup-work`) に置き、起動したときに残骸を消す。DB の写しを含むので OS の一時ディレクトリには置かない。
  - zip はメモリに載せず流す。途中で失敗したら接続を切り、ブラウザーにダウンロードの失敗として見せる (途中までの zip を正常に届いたように見せない)。
  - ファイル名は画面が `download` 属性で付ける (`weblav-backup-YYYYMMDD-HHMM.zip`)。日時を利用者の時刻で入れるため。
- **戻すのは2段にする**。受け取ったファイルをいったん置いて目録を返し、画面で作った日時と版を確かめてもらってから、置いたものの id を指して戻す。
  - 置くのは最後に受け取った1つだけで、30分で期限切れにする。受け取る大きさに上限は設けない (DB の全部が入るため)。
    期限切れのものは時間では掃除せず、次に受け取るか戻すとき、または起動し直したときに消す。残っても1つ分で済む。
  - 戻すのに失敗したら、受け取ったものは置き直す。ディスクの空き不足のような一時的な失敗で、大きなファイルを送り直させないため。
  - 今より新しい DB の版で作ったものは戻せない (422)。古い版のものは、戻すときにマイグレーションで今の形まで上げる。
- **置き換えは、今の DB の表の中身を1つのトランザクションで入れ替える**。DB のファイルは差し替えない。接続のプールが `AppState` を通して各所に配られていて、閉じ直せないため。
  - 取り出した DB を検査 (`quick_check`・版・マイグレーション・`foreign_key_check`) してから入れ替える。途中で失敗しても今の DB は変わらない。
  - アーカイブの走査中は 409 にする。
- **戻すと、全員のセッションを消す**。戻した DB では、同じ利用者 id が別の人を指しうるため。戻した本人もログインし直す。
  - **消したセッションを書き戻させない** (`session::Store`)。`with_always_save` なので、戻す前に始まった要求 (大きなアップロードなど) は、応答のときにセッションを保存し直す。`SqliteStore` の保存は行が無ければ作るので、そのままでは消したセッションが生き返る。
    消すのと同じトランザクションで、消す前に id をメモリに登録し、保存の直後に登録済みなら消し直す。
  - **残る隙間は受け入れる**。戻す前に利用者を確かめた要求は、戻した後もその利用者として処理を終える (コンテンツの作成なら、戻した DB に同じ利用者 id を作成者として入れる。その id が無ければ失敗する)。
    戻す前にパスワードを確かめたログインが、戻した後にセッションを作ることもある。どちらも戻す瞬間に重なった要求だけで、止める仕組みを持つほどではない。
- **セットアップの画面から戻したときは、ログインさせない**。戻したデータの管理者でログインし直してもらう。
  断り方・ループバックとトークンの要求は「初回セットアップ」と同じ。トークンは multipart の中でなく `x-setup-token` ヘッダで受ける。ファイルを受け取り終える前に確かめるため。

### ユーザー名の変更

- 本人はアカウントのページから自分のユーザー名を、管理者はユーザー管理から自分以外のユーザー名を変えられる。
- どちらもパスワードの確かめ直しを求める (→ 「操作の前のパスワードの確認」)。ユーザー名はログインとリカバリコードでの戻しに使うので、開いたままの画面から変えられると本人が入れなくなるため。
- 重なりは作成と同じく、大文字小文字を区別せずに断る。セッションは user id で持つので、変えてもログインは切れない。
- リカバリコードはそのまま使えるが、控え (ファイル・印刷) に書いたユーザー名は古いまま残る。戻すときは新しいユーザー名を入れるよう、マニュアルに書く。

### リカバリコード

パスワードを忘れたとき、自分で戻れるようにする。管理者が1人だけなら、その管理者が戻れる道はこれだけ。
「サーバーの PC の前にいる人」を証明にする形 (CLI やループバックの画面) は採らない。教室の PC のように何人もが触る PC では、戻し方を知っている人なら誰でも管理者になれてしまうため。
秘密の質問も採らない。答えは聞き出せたり調べられたりするので、使わせてはならないとされている ([NIST SP 800-63B-4](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-63B-4.pdf))。

- **コードは1人に1つ**。ロールによらず、誰でも自分のコードを持てる。`users.recovery_code_hash` (NULL 可) に、パスワードと同じ Argon2 でハッシュを持つ。コードそのものは保存しない。
  - ロールを変えても消さない。
  - 管理者がパスワードを再設定したら消す。パスワードを知った人が作ったコードで、再設定の後にまた取り戻されないため。本人は作り直す。
- **形は 20 文字 (Crockford の base32、100 bit)**。5 文字ずつ `-` で区切って見せる。入力では区切り・大文字小文字・紛らわしい字 (`O`/`0`・`I`/`L`/`1`) の違いを許す。
- **見せるのは作ったときの1回だけ**。コピー・テキストファイルでの保存・印刷を出し、「保管しました」を押すまで先へ進ませない。
  - 最初の管理者は、セットアップで作った直後に見せてから管理画面へ送る (→ 「初回セットアップ」)。
  - ほかの人は、アカウントのページで作る。作り直すと前のものは無効になる。パスワードの確かめ直しを求める (→ 「操作の前のパスワードの確認」)。
  - 作った時刻 (`users.recovery_code_created_at`) を持ち、アカウントのページに作った日を出す。控えに書いた作成日時と見比べ、手元の控えが今使えるものか分かるようにするため。コードを消すとき (管理者の再設定) は一緒に消す。
  - 管理者になったのにまだ無い人には、管理画面の上に作るよう促す帯を出す。`user` には出さない。管理者に再設定してもらう道もあるため。
- **戻し方**: ログイン画面の「パスワードを忘れた」から、ユーザー名・コード・新しいパスワードを入れる。
  - 通ったら、パスワードを替え、コードを使い切ってログインさせる。続けて新しいコードを作って見せる (1回きりにして、盗み見られたコードを使い回させない)。
  - ほかの端末のログインは切らない。パスワードの変更・再設定と同じ扱い (利用者ごとにセッションを消す仕組みを持たない)。
  - LAN のどの端末からでも使える。コードそのものが証明なので、場所で絞る必要がない。
  - 断る理由は区別しない (ユーザーがいない・コードが無い・違う)。ユーザー名を探らせないため。
  - 試行回数はログインと同じ `LoginRateLimiter` で絞る (ログインとは別のインスタンス)。100 bit あるので当て推量は効かず、絞るのは Argon2 の計算で CPU を食わせないため。
- **管理者が1人だけで、その管理者がコードも失くしたら、アプリの中では戻れない**。データを消してセットアップからやり直す。マニュアルにそう書く。ほかの人は、管理者に再設定してもらう。
- バックアップ (→ 「バックアップとリストア」) には `users` ごと入るので、戻すとコードも戻した時点のものになる。
