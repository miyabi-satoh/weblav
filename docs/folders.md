# フォルダーと公開できるフォルダー

## フォルダー (ブラウズ型)

- `browse_folder` / `download_content` が扱う。索引しないため DB には何も書かない。
- 閲覧の権限判定は access.md「公開範囲と匿名閲覧」による。
- 書き換えられる人は、中のファイルやサブフォルダーを「表示しない」にできる (→ 「表示しないもの」)。

### 表示しないもの

書き換えられる人は、フォルダーの中のファイルやサブフォルダーを「表示しない」にできる。見せたくないものが少し混ざるだけで、フォルダーごと登録を諦めずに済むようにするため。

- 索引しないので、外したものだけを `folder_hidden_entries` に持つ (`src/api/folder_hidden.rs`)。パスは登録先からの相対で、canonicalize した実体の綴りにする。
- 外したものは、一覧に出さないもの (ドット始まり・リンク) と同じく、一覧・ダウンロード・縮小画像・検索・リンクの一覧のファイルのどれからも外す。サブフォルダーなら中ごと外す。
- 突き合わせは、相対パスを登録先の下で canonicalize した実体のパスで行う。大文字小文字を区別しないディスクで、綴りを変えて開かれても外すため (macOS の `realpath` と Windows の `GetFinalPathNameByHandle` は実体の綴りを返す)。
- 外したものの名前を変えたり動かしたりすると、また出る。パスで覚えるため。
- 登録先を変えると捨てる。相対パスが別のものを指すため。
- 閲覧の画面の行のメニューで外し、押した行はその場で「元に戻す」の行に替える (AI が集めたリンクと同じ形、→ ai.md「AI が集めるリンク」)。編集ページの「表示しないもの」でも取り消せる。

## サーバー側ディレクトリの選択 UI

コンテンツのパスは、絶対パスのテキスト入力ではなく選択 UI で選ばせる。

### 一覧 API

`GET /api/v1/admin/fs/dirs?path=<絶対パス>` (`AuthUser`。→ access.md「ロールと操作」)

```jsonc
{
  "path": "/Users/foo/materials",   // 正規化済みの現在位置
  "parent": "/Users/foo",           // 1つ上。上位の一覧なら null
  "root": "/Users/foo",             // 現在位置を含む「公開できるフォルダー」
  "rootName": "教材",                // `root` の名前。パンくずの先頭に出す
  "selectable": true,               // ここ自身を登録先に選べるか
  "entries": [
    { "name": "chiba", "path": "/Users/foo/materials/chiba", "selectable": true }
  ]
}
```

- ディレクトリのみを返す。ファイルは返さない。
- ドット始まりは除外する。Windows では隠し属性の付いたものも除外する (→ archive.md「スキャン」)。
  シンボリックリンクは辿らない。
- `path` が空なら**登録済みの「公開できるフォルダー」を並べる**。
  ドライブの一覧ではない。名前は登録した名前にする (フルパスを出さない。同じ名前は登録時に拒むので見分けられる)。
- **登録済みのフォルダーの外は 422**。一覧そのものを見せない。
- `root` は**パンくずを辿れるところから始める**ために返す。
  これが無いと、上位の階層が押せる形で出て、押すと 422 になる。
- **エントリには名前と併せて絶対パスも載せる**。名前だけを返してクライアント側で
  連結させると、パス区切り文字とドライブルートの扱いの差がフロントの分岐になる。
- 読み取り権限が無いディレクトリは、開こうとした時点でエラーを返す
  (一覧からは消さない。存在は見えてよい)。

### 公開できるフォルダー

**コンテンツに使えるパスは、設置者が登録したフォルダーの配下だけ**にする。
拒否リスト (「ここは選べない」の列挙) は持たない。

拒否リストを捨てた理由:

- 網羅できない。macOS の `/private` を登録すれば `/etc`・`/var` ごと入る、という穴が
  残り、塞ごうとするとリストが際限なく伸びる。
- セルフホストで、設置者が自分の PC から何を配るかを選ぶ道具である以上、
  選べる範囲は設置者に任せてよい。`C:\Windows` でもホームでも、設置者が選ぶなら選べる。
- 安全な範囲を WebLAV が定義し始めると、include/exclude に発展する。**設置者自身に選ばせるなら WebLAV が定義を持たない**。
  include/exclude は持たない、と最初に線を引く。

**誤指定に対する防御の主役は、これまでどおり確認ダイアログ** (件数と実効的な閲覧範囲の
提示、→ 「登録前の確認」)。拒否リストは元々「明白な事故だけを止める」位置づけだった。

#### 登録と削除

`GET` / `POST /api/v1/admin/roots`、`PUT` / `DELETE /api/v1/admin/roots/{id}`。

- 登録 (`POST`) できるのは**サーバーの PC の前にいる管理者**だけ
  (`LocalRequest` + `AdminUser`、access.md「初回セットアップ」と同じループバックの判定)。
  公開する範囲を広げる操作だけを PC の前に限る。通信が暗号化されないので、LAN で管理者のパスワードを盗まれても、範囲を広げられないようにするため。
  LAN の端末からは、登録とフォルダー選択の口があること自体を見せずに 404 にする。
- 一覧・名前の変更・削除は、LAN の端末の管理者もできる (`AdminUser`)。どれも範囲を広げない。
  管理者は LAN の端末からコンテンツを消せるので、削除だけを PC の前に残しても守れるものが増えない。
- 画面は管理画面のタブを1つ増やす。「フォルダーを追加...」は、サーバーの PC から開いたときだけ出す。
  LAN の端末から開いたときは、追加できる場所の案内を出し、削除の確認にも登録し直せる場所を添える。
- フォルダーは **OS 標準のフォルダー選択の窓**で選ばせる (→ 下の「選び方」)。
- 登録時に拒むのは4つだけ。存在しない・ディレクトリでない・WebLAV 自身の置き場の中・同じフォルダーの二重登録。
  - **入れ子は許す**。狭い範囲を登録した後で外側も公開したくなったとき、内側を消してからでないと登録できないのは手間なため。
    見てよい範囲の判定は「どれかの中にあるか」なので、重なっても結果は変わらない。
  - 入れ子では、場所の表示 (→ 下の「名前」) とパンくずの起点は**最も外側**にする。
    内側にすると、外側から辿って内側へ入ったときに起点が切り替わり、「上へ」で外側へ戻れない。内側の登録は、最初の一覧に並ぶ近道として働く。
- 削除の確認には**外すと見られなくなるコンテンツの件数**を出す (ほかの登録にも含まれるものは数えない)。
  コンテンツの登録自体は消さないので、登録し直せばまた見られる。
- **削除しても行は消さず、削除済みの印を付ける** (`deleted_at`)。配信・ピッカー・一覧・二重登録の判定からは外し、
  場所の表示 (→ 下の「名前」) だけに使う。残ったコンテンツのどこまでが起点だったかを、あとから分かるようにするため。
  同じパスを登録し直したら、その行の印を消して戻す (`path` の UNIQUE はそのまま)。
- 保存するのは canonicalize 済みの絶対パス。比較が実体パス同士になるようにするため。

#### 選び方

`POST /api/v1/admin/roots/pick` (`LocalRequest` + `AdminUser`) で、**サーバーの PC に OS 標準のフォルダー選択の窓を出し**、選ばれた絶対パスを返す
(`{ "path": "..." }`、キャンセルなら `null`)。登録はしない。画面は返ったパスをそのまま `POST /api/v1/admin/roots` へ送る。

- OS の窓にする理由:
  - Windows はエクスプローラー、macOS は Finder と同じ窓なので、見慣れた操作で選べる (→ ui.md「UI 全般」)。自前のピッカーを辿らせるより迷わない。
  - 3つの OS で同じ手順になる (→ distribution.md「ビルド・配布の方法」)。窓は OS ごとに違っても、「押すと窓が出て、選ぶ」は変わらない。
  - macOS のサンドボックスでは、利用者が OS の窓で選んだ場所しか読めない (→ distribution.md「ビルド・配布の方法」)。
- 窓を出すのは `rfd`。ブラウザーで押した操作の続きなので、**窓はブラウザーより前に出す**。rfd は前に出さないので、呼ぶ側で手当てする。macOS は自分を前面のアプリにしてから出す。Windows は前面にいないプロセスが窓を前面にするのを許さないので、最前面に置いた見えない窓を持ち主にして、その上に出す。窓は閉じるまでほかのアプリより上に残り、タスクバーにも出ないが、裏に隠れて見失うよりよい (見失うと、次に押しても 409 になる)。Linux は手当てしていない (実機で確かめていない)。
- **窓は同時に1つだけ**。開いている間の2つ目は 409。
  ブラウザー側で待つのをやめても (タブを閉じるなど)、窓が閉じるまでは開いている扱いにする。窓は PC の前に残っているため。
- 窓を出す仕組みは、実行ファイルごとに `AppState` へ渡す (`folder_picker::FolderPicker`)。
  - macOS の窓 (NSOpenPanel) はメインスレッドでしか開けない。トレイ版 (`weblav`) はメインスレッドで回っているトレイのイベントループに頼み、`weblav-service` はメインスレッドで頼みを待つ。
  - テストは、決まったパスを返すものに差し替える。
- 登録時の検証 (上の「登録と削除」の4つ) はそのまま掛ける。窓では weblav 自身の置き場や登録済みのフォルダーも選べてしまうので、422 には理由を画面に出せる内訳を付ける (`rootInsideOwnDirs`・`rootAlreadyRegistered`)。

#### 名前

登録するときに名前を付ける。**コンテンツの登録側の画面では、起点のフルパスの代わりに名前を出し**、そこから先だけを続ける
(例:「教材 / 英検 / 2024」)。編集者 (`user`) にも見える画面で、サーバーのパソコンのフォルダー構成を見せないため。

- 追加の画面では名前を入力させず、フォルダー名にする (ドライブのルートのようにフォルダー名が無ければパスのまま)。
  同じ名前があれば `(1)`、`(2)` と連番を付ける (→ ui.md「UI 全般」の「作成の入力は必要最小限にする」)。
- **指定した名前が他と同じなら拒む** (大文字小文字だけの違いも同じとみなす。削除済みを除いた NOCASE の部分ユニークインデックス)。
  名前がフルパスの代わりに見分ける手掛かりなので、重なるとピッカーや場所の表示で取り違える。
- 名前は後から変えられる (`PUT /api/v1/admin/roots/{id}`)。空ならフォルダー名に戻す (重なるなら連番)。
- **隠すのは画面だけ**。API は今までどおり絶対パスを返し (access.md「管理画面の一覧が `user` に見えること」はそのまま)、場所の表示用に名前と
  そこから先のパス (`AdminContentResponse` の `rootName`・`pathInRoot`、ディレクトリ一覧の `rootName`) を足す。
  編集者はもともとコンテンツの登録を任せている相手で、狙いは画面にフォルダー構成を出さないことにある。
  場所を「公開できるフォルダーの ID と、その先のパス」でやり取りする形にすると、登録・ピッカー・件数の API の受け渡しが全部変わる。
- 「公開できるフォルダー」の画面では、名前とフルパスの両方を出す。開けるのは管理者だけで、
  実際のフォルダーを登録・削除する画面なので、どこを指すかが要る。
- **登録を削除した後に残ったコンテンツの場所**は、管理者にはフルパスを出す。どこを登録し直せばよいかが分かるため。
  それ以外の人には「(見つからない公開できるフォルダー) / その先」と出し、もともと隠していた起点のパスは見せない
  (選べたその先は見えてよい)。どの記録にも含まれない場所は、起点が分からないので「(見つからない公開できるフォルダー)」だけにする。
  `AdminContentResponse` は `rootDeleted` を返し、出し分けは画面で行う (隠すのは画面だけ、は同じ)。

#### 唯一の例外: WebLAV 自身の置き場

**`AppDirs` の `config_dir` (設定ファイル) と `data_dir` (DB とセッション鍵) そのものとその中は、どこからも見せない** (`AppState::own_dirs`)。
設置者が意識して選ぶ場所ではなく、親フォルダーを選んだ結果として巻き込まれる場所のため。

- **祖先は登録できる** (`C:\` など)。守りたいのは中身が出ないことで、親フォルダーを選べないことではない。
  祖先を拒むと、`C:\` のような広い場所を選んだ設置者に、中の一部のせいで拒まれた理由が伝わらない。
- 設定の置き場も外す。設定ファイルには秘密を書かない前提 (`session.secret` は空のままにし、鍵はデータ側の `session.key` に置く) だが、`session.secret` は書けるので、前提が崩れたときに出ないようにする。
- 置き場の中は、登録先に選べず (422)、フォルダーの一覧・スキャンに出さず、配信も 404 にする。
  置き場そのものも一覧に並べない (選んでも中身が出ないため)。
- 判定は `roots::OwnDirs` (実体パス同士で比べる)。エントリごとに比べる一覧・走査があるので、
  置き場の実体パスは要求ごとに1回だけ求めて持ち回る。

#### 判定はパスを使う操作すべてに掛ける

判定を関数1つに切り出し (`roots::is_within_roots(roots, canonical, own_dirs)`)、次の全てから呼ぶ。

- `validate_folder_path` (`folder` / `archive` の作成・更新)
- ディレクトリ一覧 API (`selectable` の値と、辿れる範囲、→ 「一覧 API」)
- ファイル数の確認 API (→ 「登録前の確認」)
- `archive` の再走査
- `folder` のブラウズ・ダウンロードと `archive` のアイテム配信 (`contents::resolve_path`)
  - 配信では、**一覧に出さないもの (→ archive.md「スキャン」) も通さない** (`fs::has_hidden_component`)。
    公開できるフォルダーから先の各階層に、ドット始まり・シンボリックリンク・Windows の隠し属性があれば 404。
    一覧に出ないだけでパスを知っていれば落とせる、という食い違いを残さないため。
    名前は要求と実体の両方で見る (`fs::has_dot_component`)。Windows の 8.3 短縮名 (`ENV~1`) が `.env` に解決されるため。
    Windows では `:` を含む名前も 404 にする (代替データストリーム `a.mp3:stream`)。

登録時の検証だけでは足りない。書き込み経路にしか掛からないので、**登録を消したあとの行**や、
置き場を移したあとの行がそのまま配信され続ける。
通らなかったとき、閲覧者も通る経路 (ブラウズ・ダウンロード・アイテム配信) は
404 にして存在を伏せる。再走査と登録はログインした人だけの操作なので、理由の分かる 422 にする。

判定は `canonicalize` 済みのパスに対して行う。シンボリックリンク経由で
外を指す入力を弾くため。登録済みのフォルダーは判定のたびに DB から読む
(件数は多くても数件で、キャッシュを持つと登録・削除の直後に古い判定が残る)。

#### ルートの外は理由を1つに寄せる

ディレクトリ選択・ファイル数の確認・`folder` / `archive` の登録は、ログイン済みなら `role` を問わず叩ける (→ access.md「ロールと操作」)。
「存在しない」と「ディレクトリでない」の区別がルートの外にも及ぶと、任意の絶対パスの存在を確かめる道具になるので、**ルートの外は文言を1つに寄せる** (`fs::outside_roots`)。
ルートの中は区別したままにする (選んだのがフォルダーでなかった、という直せる誤りを伝えるため)。

判定の順は「絶対パスか → `canonicalize` → ルートの内外 → ディレクトリか」で、**`canonicalize` は1回だけ**。
2回呼ぶと、存在するパスと存在しないパスで触る I/O の量が変わる。
絶対パスかどうかは入力の文字列だけで決まるので、先に区別して返してよい。

**処理時間の差までは消さない (受容)**。
`canonicalize` 自体の所要時間が入力に依存する (実在する前半部分の深さ、シンボリックリンクの段数) ため、失敗側に同じだけの処理を足しても定数時間にはならず、定数時間に見えるコードが残るだけになる。
差はマイクロ秒の単位で、手前にある DB 参照 (`roots::load_roots`)・`spawn_blocking` の待ち・LAN の揺らぎに埋もれる。
読み取るには、認証済みの相手が同じパスを何千回も測る必要がある。

#### 登録が0件のとき

コンテンツ側は、**種別を選ぶ画面の時点で** `folder` / `archive` を押せなくし、理由を出す。
移行をしない (下記) ので、必ず0件から始まる。

#### 既存コンテンツの移行はしない

未リリースなので、開発用・検証用の環境は登録し直す。
パスから逆算してルートを起こす仕組みは作らない。

### NAS と外付けのディスク

- NAS の共有フォルダーや外付けのディスクも、OS から読めれば登録できる。WebLAV は接続の情報 (サーバー・共有名・パスワード) を持たず、つなぐのは OS に任せる。
- 選び方は手元のフォルダーと同じ OS の窓 (→ 「選び方」)。macOS の Finder の窓は「ネットワーク」や接続済みのサーバーから、Windows のエクスプローラーの窓は「ネットワーク」から共有をたどれる。
  初めてつなぐ共有はパスワードを OS が聞き、キーチェーン (Windows は資格情報マネージャー) に保存できる。保存しないと、外れた後につなぎ直せない。
- **UNC パスは拒まない**。バックエンドは `\\` 始まりのパスを特別扱いせず、`canonicalize` が通れば受け入れる。共有のルート (`\\server\share`) 自体も、設置者が選ぶなら登録できる (→ 「公開できるフォルダー」)。
  Windows で割り当てたドライブ (`Z:\`) から選んでも、`canonicalize` が UNC の形 (`\\?\UNC\...`) で返すので、登録は UNC パスになる。ドライブの割り当てが戻る前に起動しても読め、同じ共有を UNC で選び直すと登録済みとして断る。
- テキスト入力の併設はしない。
- NAS の共有を登録するときは、その共有に書き込める人を信頼できる人に限る (→ `contents::resolve_path` のコメント)。

#### つながっているかの確かめ

NAS が落ちていると、その共有を触った所でファイル操作が長く戻らない。登録済みのフォルダーの配下を触る前に、そのフォルダーを開けて中を1件読めるかを確かめ、時間で打ち切る (`folder_reach`)。
確かめの操作そのものは止められないので、裏で戻るまで走らせておき、同じフォルダーへの確かめは1本にまとめる。

- 開こうとしているフォルダーは 20 秒まで待つ。眠っている NAS やディスクの HDD が回り出すのを待つため。
- 一覧や検索で並べるだけのほかのフォルダーは 1 秒で打ち切り、その要求では外す。手元のフォルダーの要求を、NAS のために待たせないため。
- 結果は、読めたら 2 秒、読めなかったら 5 秒使い回す。一覧の縮小画像のように、短い間に同じフォルダーへ要求が重なるため。
- 様子は3つに分ける。
  - 読める。
  - フォルダーが無い: 共有やディスクはある。今までどおり、消されたフォルダーと同じに扱う (404・`archiveFolderMissing` など)。
  - つながらない: 共有やディスクごと無い、または時間内に返事が無い。503 `folder_unreachable` を返す。見る人には、しばらくしてから開き直し、続けば管理者に伝えるよう出す (見る人は NAS を直せないため)。
- 外れることのある場所 (ここごと無ければ「つながらない」): macOS は `/Volumes/<名前>`、Ubuntu は `/run/user/<uid>/gvfs/<共有>`・`/media/<ユーザー>/<名前>`、Windows は UNC の共有とドライブ。
- 公開できるフォルダーの一覧には、行ごとに様子 (`status`) を出す。

#### つなぎ直し

共有やディスクごと無いときは、OS につなぎ直しを頼んでから確かめ直す。つながらない NAS へ要求ごとにマウントを試みないよう、30 秒に1回までにする。パスワードは OS が保存したものを使い、窓は出さない。

- macOS: 窓で選んだときのブックマーク (→ distribution.md「ビルド・配布の方法」) を、マウントを許して解決する。起動のときの許可の戻しではマウントしない。つながらない NAS を待って起動が遅れないため。
- Ubuntu: gvfs の共有 (`smb-share:server=...,share=...`) なら `gio mount smb://<サーバー>/<共有>`。
- Windows: UNC パスは開くときに OS がつなぐので、何もしない。

### 登録前の確認

`GET /api/v1/admin/fs/count?path=<絶対パス>&extensions=<カンマ区切り>` (`AuthUser`。→ access.md「ロールと操作」)

- 対象になるファイル数を数えて返す。**`folder` と `archive` の両方で**呼ぶ。
  件数の提示は誤指定に気づかせるためのもので、
  アイテムが既定で非公開かどうかとは別の話。`archive` でもパスの指定を
  間違えれば巨大なツリーを索引してしまう。
- `extensions` を指定すると、その拡張子だけを数える (`archive` の登録時に
  拡張子フィルタを反映した件数を出すため)。省略時は全ファイル。
- 数え方はスキャンと揃える (ドット始まりとシンボリックリンクを除外。→ archive.md「スキャン」)。
  ダイアログの件数と、登録後に実際に索引される件数がずれないようにするため。
- 上限 (20,000件) を超えたら打ち切り、打ち切った旨のフラグを添えて返す。ちょうど上限なら打ち切らない (スキャンの上限と揃える)。
  誤って巨大なツリーを指したときにダイアログが固まらないようにするため。
- この件数は確認ダイアログのためにその場で数えるだけで、保持しない。

確認ダイアログには、件数と、そのコンテンツの実効的な閲覧範囲の両方を出す。
文言は種類と実効的な公開範囲で変える。

| 条件 | 文言 |
|---|---|
| `folder` かつ実効 `public` | 「LAN 内の誰でも、この N 個すべてを閲覧できます」 |
| `folder` かつ実効 `authenticated` | 「ログインした人だけが閲覧できます」 |
| `folder` かつ実効 `private` | 「あなただけが閲覧できます」 |
| `folder` かつ実効 `hidden` | 「閲覧の場には表示されません。公開範囲を変えるまで、誰も閲覧できません」 |
| `archive` | 「N 個のファイルが索引されます。公開するファイルは、登録後に個別に選びます」 |

実効的な公開範囲は、フォームの `visibility` に、選んだ親グループと祖先の公開範囲を重ねたもの (→ access.md「親が外れるときの公開範囲」)。
設定ではなく実効的な公開範囲で文言を選ぶ。「非表示」のグループの中の「誰でも」を「LAN 内の誰でも」と案内すると、実際と違う範囲を示すことになるため。
